# Test localization and layout direction

Use this guide to verify Android string resources, locale-sensitive formatting, translated interactions, and RTL layout in Compose local tests. Use a device or established rendering suite for glyph shaping, clipping, font fallback, and system language integration.

## Choose the locale boundary

| Question | Local approach | Separate evidence |
| --- | --- | --- |
| Does Android resolve the German string? | Configure resource locale before host creation | Device app-language selection |
| Is a formatter correct for a locale and zone? | Pure formatter test with explicit inputs | Platform-specific ICU differences where relevant |
| Does a component mirror in RTL? | Provide RTL layout direction and inspect behavior or relative bounds | Device rendering and system RTL configuration |
| Can users finish a translated flow? | Parameterized expected labels and real actions | Real IME and assistive technology behavior |
| Does language selection persist? | Real preference store with isolated data | App restart or OS-managed language integration |
| Does the server return localized content? | Real client header and service contract tests | End-to-end service response |
| Do translated labels fit? | Text-layout overflow observation where available | Locale-specific rendering baselines and review |

Android resource locale, Java's default locale, Compose layout direction, time zone, and the client's language header are separate inputs. Changing one does not reliably change the others.

## Configure resources before mounting

Put resource-backed tests in an Android module's `src/test` with Robolectric, resources enabled, and a declared activity host. Use [the setup reference](../references/setup.md). Select the resource configuration before the rule launches the host.

These illustrative resource files belong to the consuming app, not the installed skill. Put the default strings in `app/src/main/res/values/strings.xml`.

```xml
<resources>
    <string name="sign_in">Sign in</string>
    <string name="welcome">Welcome</string>
</resources>
```

Put the German strings in `app/src/main/res/values-de/strings.xml`.

```xml
<resources>
    <string name="sign_in">Anmelden</string>
    <string name="welcome">Willkommen</string>
</resources>
```

The following illustrative complete test uses those resources, Material3, Compose UI 1.12.1, JUnit 4, and Robolectric. Replace `example.app.R` with the consuming module's generated resource namespace. It is not compiled fixture code.

```kotlin
import androidx.compose.foundation.layout.Column
import androidx.compose.material3.Button
import androidx.compose.material3.MaterialTheme
import androidx.compose.material3.Text
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.remember
import androidx.compose.runtime.setValue
import androidx.compose.ui.res.stringResource
import androidx.compose.ui.test.assertIsDisplayed
import androidx.compose.ui.test.junit4.v2.createComposeRule
import androidx.compose.ui.test.onNodeWithText
import androidx.compose.ui.test.performClick
import example.app.R
import org.junit.Rule
import org.junit.Test
import org.junit.runner.RunWith
import org.robolectric.RobolectricTestRunner
import org.robolectric.annotation.Config
import org.robolectric.annotation.LooperMode

@RunWith(RobolectricTestRunner::class)
@Config(sdk = [35], qualifiers = "de")
@LooperMode(LooperMode.Mode.PAUSED)
class GermanSignInTest {
	@get:Rule val compose = createComposeRule()

	@Test fun translatedActionShowsTranslatedResult() {
		compose.setContent {
			var signedIn by remember { mutableStateOf(false) }
			MaterialTheme {
				Column {
					Button(onClick = { signedIn = true }) {
						Text(stringResource(R.string.sign_in))
					}
					if (signedIn) Text(stringResource(R.string.welcome))
				}
			}
		}
		compose.onNodeWithText("Anmelden").performClick()
		compose.onNodeWithText("Willkommen").assertIsDisplayed()
		compose.onNodeWithText("Welcome").assertDoesNotExist()
	}
}
```

The sample proves resource selection and an interaction using translated labels. It does not implement authentication. For a real sign-in flow, mount the real screen with a controlled session boundary.

Do not set only `Locale.setDefault(Locale.GERMAN)` and assume Android resources changed. Robolectric qualifiers configure Android resources. Formatters that read JVM defaults may still need explicit inputs or controlled defaults.

## Cover a small locale matrix

Choose locales that expose different risks rather than repeating every test for every translation.

| Locale case | Risk to cover |
| --- | --- |
| Default English | Baseline behavior and fallback resources |
| German or another long-label language | Expansion and narrow-width interaction |
| Japanese or another CJK language | Font fallback, wrapping, and input |
| Arabic or Hebrew | RTL mirroring and mixed-direction content |
| A locale with several plural categories | Quantity rules and substituted values |

Use independently configured test classes or methods so each host begins with the intended resource locale. If the project uses a parameterized runner, ensure it remains compatible with its Robolectric runner configuration. Do not replace the runner with JUnit's ordinary parameterized runner and lose Android behavior accidentally.

For a translated journey, parameterize the expected action and result labels alongside the locale. Stable tags can identify structural containers, but keep explicit translated-text checks. A test that uses only tags can pass with every visible label left in English.

Use hardcoded expected translations for a small approved set when verifying translation selection. Looking up the expected value through the same resource call as the component can pass when both fall back to English.

## Test language switching and persistence

Test the app's actual ownership model. Some apps use OS-managed per-app locales. Others store an in-app language preference and recreate the host or update a provider.

A local language-picker test can prove:

1. The current locale's heading is visible.
2. Opening **Language** displays available options.
3. Selecting **Deutsch** calls the real language-selection path.
4. The intended translated content appears after the app's update mechanism.
5. The stored preference contains the chosen language tag.

If switching recreates the activity, use an activity-host test with one content owner. Do not call `setContent` again on an activity that already sets its own content.

For persistence, write through the real preference boundary, create a new reader using the same isolated store, and verify the saved language. A fake retaining a field proves only that fake's lifetime.

A device test should select a per-app language through the supported mechanism, relaunch the app, and verify the resulting UI and supported language list. Local disposal and remounting are not proof of OS integration or process death.

For localized server content, inspect the actual client's language header or locale variable in a client contract test. Changing Android resources does not automatically add `Accept-Language` to requests.

## Test RTL layout separately

For a focused component case, provide `LocalLayoutDirection` without changing its resource locale. This isolates layout behavior from translation selection.

This illustrative fragment assumes a project composable `ProfileActions` and a hosted rule. It requires Compose runtime and UI platform imports shown here.

```kotlin
import androidx.compose.runtime.CompositionLocalProvider
import androidx.compose.ui.platform.LocalLayoutDirection
import androidx.compose.ui.unit.LayoutDirection

compose.setContent {
	CompositionLocalProvider(LocalLayoutDirection provides LayoutDirection.Rtl) {
		ProfileActions()
	}
}
```

For an integrated Arabic case, configure Arabic resources before host creation and test the app's actual direction policy. Do not force RTL in the test and claim that the app automatically chooses RTL correctly.

Assert relative positions only where placement is a contract. For a leading navigation pane, compare its bounds with the content bounds in LTR and RTL. Name the intended relation explicitly. Do not assert every absolute coordinate.

Test directional icons and gestures too. A back arrow may mirror while a media-play icon should not. A swipe action's semantic meaning may remain **Dismiss** even when the physical direction changes.

Input focus order and accessibility traversal are not proven by mirrored bounds. Add keyboard and device TalkBack cases for important RTL journeys.

## Pin date, number, and currency inputs

Pass locale, zone, currency, and instant explicitly into the formatting boundary. Do not rely on the host machine's date or default time zone.

This illustrative complete pure JUnit test requires only the JDK and JUnit 4. It demonstrates fixed input selection, not the app's production formatter. In the consuming project, call the production formatter with the same explicit inputs.

```kotlin
import java.time.Instant
import java.time.ZoneId
import java.time.format.DateTimeFormatter
import java.util.Locale
import org.junit.Assert.assertEquals
import org.junit.Test

class DateFormattingExampleTest {
	@Test fun zoneDeterminesTheCalendarDate() {
		val instant = Instant.parse("2025-01-01T00:30:00Z")
		val formatter = DateTimeFormatter.ofPattern("uuuu-MM-dd", Locale.US)
		assertEquals("2024-12-31", formatter.withZone(ZoneId.of("America/Los_Angeles")).format(instant))
		assertEquals("2025-01-01", formatter.withZone(ZoneId.of("UTC")).format(instant))
	}
}
```

For the real formatter, add cases for decimal separators, grouping, negative values, currency rounding, and zero-decimal currencies. Locale does not determine business currency. A German-speaking user can view USD prices.

Keep exact Unicode spacing when the product depends on it. French formatting may contain nonbreaking spaces rather than ASCII spaces. Inspect code points when an apparently identical expected value fails. Do not strip all whitespace to hide the distinction.

Pin the runtime when exact ICU output is a baseline. Pure JDK formatters and Android ICU can differ. Test the implementation actually used by the app and avoid claiming one is proof of the other.

## Check plurals and translation fallback

For plural resources, test relevant quantity categories for each selected locale. Include zero, one, two, and representative larger values according to the locale's rules. The plural category and the number inserted into the string are separate inputs to Android plural-resource lookup.

For supported languages, validate resource coverage with the project's resource tooling and review critical copy explicitly. UI tests alone cannot visit every string resource.

For unsupported languages, assert the intended fallback. For partially translated locales, distinguish deliberate fallback from an accidental missing translation. A test that rejects every English word can fail on product names while missing other resource defects.

Test formatted placeholders with real synthetic names and counts. Raw `%1$s`, unresolved keys, or untranslated placeholders should not appear in user-facing content. Do not use a broad placeholder regex as the only translation check.

## Check long text and bidirectional content

Use long approved translations and pseudolocalization in a rendering or device matrix. Combine them with a narrow width and large font scale for critical buttons, dialogs, navigation, and error messages.

A displayed semantics node does not prove that all text fits. Where a component exposes `TextLayoutResult`, a focused test can inspect overflow through the appropriate test API or a component-owned layout callback. Keep that check separate from semantics presence.

For mixed Arabic names and LTR email addresses, assert content locally and inspect actual rendering separately. A positive width does not prove correct bidirectional ordering or lack of overlap.

Test selection and editing with synthetic non-Latin input. Semantics text input proves the component's editing path, not real keyboard composition, autocorrect, or IME candidate behavior. Add device cases for those claims.

## Separate visual regression evidence

Store rendering baselines by locale, layout direction, width, font scale, theme, and rendering environment. Compare critical controls as well as whole screens when the suite supports both.

Use a deterministic bundled font where the test contract calls for one. For downloadable fonts, synchronize the actual font-loading mechanism or use a controlled font source. There is no Android equivalent of awaiting browser `document.fonts.ready` in a Compose test.

Keep device baselines distinct from Robolectric output. Approving a JVM screenshot must not imply device glyph shaping, antialiasing, or GPU fidelity.

## Isolate locale state and synchronization

Prefer explicit locale and zone parameters to global changes. If a test must change `Locale` or `TimeZone` defaults, capture and restore them in teardown, including on failure. Do not run tests that mutate the same process globals concurrently.

Create fresh language preferences, caches, and formatter instances per test. A cached formatter created before the locale change can keep the old locale even when resources have updated.

Compose synchronization does not complete preference writes or activity recreation automatically in every setup. Observe the real state transition with the appropriate lifecycle API or a bounded condition. Do not use an arbitrary sleep after choosing a language.

## Avoid misleading localization tests

| Anti-pattern | Failure mechanism | Correction |
| --- | --- | --- |
| Set JVM default locale only | Android resources may retain the original configuration | Configure resource locale before host creation |
| Use only tags in translated flows | English fallback still passes | Assert approved translated labels too |
| Fetch expected text from the same resource path | Both sides can make the same fallback mistake | Use independent expected copy for selected critical strings |
| Infer currency from locale | User currency and language are independent | Pass explicit currency |
| Assert semantics presence means no clipping | Clipped text can remain in semantics | Add layout or rendering evidence |
| Force RTL and claim locale integration | App direction selection was bypassed | Separate direction-isolation and integrated locale tests |
| Leave global locale changed | Later tests inherit another language | Restore globals and isolate parallel execution |

## Troubleshoot failures

| Symptom | Observe | Correction |
| --- | --- | --- |
| German test shows English | Host configuration and resource qualifiers | Configure locale before rule launch and include Android resources |
| Labels change but numbers do not | Formatter construction and default locale | Inject locale or recreate the formatter at the actual owner |
| Date differs only in CI | Instant, default zone, runtime | Pin explicit time and zone inputs |
| RTL text appears but layout stays LTR | Layout direction and app locale policy | Test and repair the actual direction source |
| Visually identical currency assertion fails | Unicode code points | Use the correct spacing and symbol contract |
| Language switch returns old text | Recreation, stale context, cache | Observe the new owner and invalidate app-owned cached values |
| Screenshot uses fallback glyphs | Font source and loading state | Make font dependencies deterministic and verify on the target layer |

## Review checklist

- [ ] Resource locale, formatter locale, zone, and layout direction are deliberate.
- [ ] Critical translated actions have independent expected labels.
- [ ] RTL behavior is tested independently and through the app's locale policy.
- [ ] Dates and currencies use explicit business inputs.
- [ ] Plural, fallback, and placeholder behavior is covered.
- [ ] Font, clipping, and bidirectional claims have rendering or device evidence.
- [ ] Locale globals and preference stores cannot leak between tests.
